## Contributor License Agreement

This project welcomes contributions and suggestions. Most contributions require
you to agree to a Contributor License Agreement (CLA) declaring that you have
the right to, and actually do, grant us the rights to use your contribution.
For details, visit <https://cla.opensource.microsoft.com>.

When you submit a pull request, a CLA bot will automatically determine whether
you need to provide a CLA and decorate the pull request appropriately. Simply
follow the instructions provided by the bot. You will only need to do this once
across all repositories using our CLA.

The repository owner must enable the Microsoft CLA integration before accepting
public contributions. This document does not attest that it is already enabled.

## Development

- Read [README.md](README.md), [docs/testing.md](docs/testing.md) and
  [docs/security.md](docs/security.md) before changing runtime behavior.
- Use the Go version declared in `go.mod` for CI checks and formatting, plus
  Docker and Buf as described in the README. Build with
  `make build` in Bash or `.\make.ps1 build` in PowerShell 7; run focused Go tests
  for the packages you change. See [command shells](docs/README.md#command-shells)
  for cross-platform helper prerequisites.
- Keep changes scoped, preserve native runtime compatibility, and add regression
  coverage for changed behavior through public interfaces.
- Run `go test` and the repository-configured Go linters for affected packages.
  Follow the existing formatting and error-handling conventions.
- Describe the behavior, tests and remaining limitations in your pull request.
  Use a task prefix when a backlog task exists. Do not include credentials,
  personal data, internal-only documents or deployment-specific access details.
- Changes to shared contracts, security controls or deployments require explicit
  review. Do not activate clusters, incur provider charges or modify cloud
  resources as part of an ordinary local test run.
- Retain third-party copyright and license notices. Describe any new dependency
  and its license in the pull request and update distribution attribution.

### Commit messages and pull requests

- Use Conventional Commits such as `fix(ci): validate inputs` or
  `chore(deps): update dependencies`. Supported types are `feat`, `fix`, `docs`,
  `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore` and `revert`.
  Scopes and breaking-change markers are optional.
- Existing `T-nnnn` task prefixes remain valid. Include task, story or issue
  references when applicable; CI does not require a task or story for every change.
- Merge and revert subjects generated by Git are accepted. An `Initial plan`
  subject is accepted only when the commit makes no file changes.
- Provide a non-empty PR description covering the changes and validation.
  Story IDs such as `US-0001` are optional.

### Documentation

Use the [documentation map](docs/content-map.md) to distinguish reader guides,
operational contracts and historical development records. The website requires
Node.js 24 and npm. From the repository root, validate documentation changes with:

These commands work in Bash and PowerShell:

```sh
npm --prefix website ci
npm --prefix website test
npm --prefix website run check
npm --prefix website run build
npm --prefix website run check-links
```

Keep the README focused on entry paths. Preserve existing source links and
installation/activation safeguards. Documentation validation must not provision
cloud resources, activate a cluster or invoke a paid provider.

#### Publishing the documentation website

The [documentation workflow](.github/workflows/pages.yml) validates pull requests
without deployment permissions. Deployment requires a trusted `main` run and the
repository variable `DOCS_PAGES_ENABLED` set to exactly `true`.

Before enabling publication, an administrator must review the selected pages,
configure GitHub Pages to use GitHub Actions, and protect the `github-pages`
environment. Confirm that organization policy permits the site's visibility:
a private repository does not automatically produce a private Pages site.

The default site is `https://microsoft.github.io/kognition/`. Set `DOCS_SITE_URL`
to an HTTPS origin and `DOCS_BASE_PATH` to an absolute path for another approved
target. The workflow retains dependency legal texts with `npm run notices`
before uploading a deployment artifact. Missing attribution blocks publication.
